# Eval-запросы для скила `meeting-protocol`

Классификатор видит только `description`, и в реальной системе оно обрезается примерно до 250 символов. Поэтому негативные запросы подобраны как «почти попадания»: в них есть слова «встреча», «совещание», «кратко», «таблица задач», но нужно другое действие.

## Запросы

| № | Запрос | Ожидание | Обоснование |
| --- | --- | --- | --- |
| 1 | Вот мои заметки с планёрки, оформи нормальный протокол: «обсудили отпуска, Катя до пт соберёт график, бюджет на корпоратив не утвердили» | Триггер | Прямая просьба оформить протокол по сырым заметкам встречи. |
| 2 | Сделай саммари вчерашнего созвона с клиентом, расшифровка ниже: … | Триггер | «Саммари созвона» по расшифровке — это итоги встречи, ядро сценария. |
| 3 | Вытащи из этих заметок, что мы решили и кто что должен сделать к какому числу | Триггер | Извлечение решений и задач с ответственными и сроками из заметок встречи. |
| 4 | Turn these meeting notes into minutes with action items: … | Триггер | Англоязычная формулировка того же сценария (meeting minutes, action items есть в description). |
| 5 | Нужен протокол совещания, потом выгружу в Word. Вот стенограмма из Zoom: … | Триггер | Протокол совещания по стенограмме с явной целью выгрузки в Word. |
| 6 | Кратко, TL;DR: что решили на ретро? Мои заметки: … | Триггер + route | Итоги встречи по заметкам с просьбой «кратко» — скил и сценарий `routes/quick_summary.md`. |
| 7 | Переведи на английский: «Встреча перенесена на четверг, повестка без изменений» | Нет | Текст про встречу, но задача — только перевод, это явное исключение в description. |
| 8 | Перескажи кратко статью «Как проводить эффективные совещания» | Нет | Пересказ статьи о совещаниях: заметок конкретной встречи нет. |
| 9 | Напиши на Python функцию, которая парсит markdown-таблицу «Задача / Ответственный / Срок» | Нет | Генерация кода, хотя упоминается формат таблицы задач. |
| 10 | Как вежливо попросить руководителя перенести встречу? | Нет | Общий вопрос о деловой коммуникации, протокол не нужен. |

## Пример: заметки → протокол

### Входной запрос

```
Оформи протокол по заметкам:

созвон по запуску мобилки v2.0, 14.10.2025, 11:00-12:00, zoom
были: Анна Смирнова (PM), Дмитрий Ковалёв (backend), Ольга Лебедева (дизайн), Игорь Петров (QA)

- релиз: сначала говорили 10.11, Игорь против — регресс не успеет за 3 дня.
  в конце Анна: окей, 12.11, окончательно
- пуши: Дмитрий доделывает API пушей, обещал до 24.10. пуши точно в релизе, согласовали
- онбординг: Ольга покажет новые макеты онбординга на следующей неделе
- аналитика: Amplitude vs оставить Firebase — не договорились, Анна хочет Amplitude, Дмитрий против (миграция событий ~2 недели)
- Игорь подготовит план регресса до 31.10
- надо бы кому-то обновить release notes для стора
- риск: платёжный SDK вендор обещал обновить к 01.11, если не успеют — оплата в v2.0 на старом SDK
- спросить у Олега из маркетинга про скриншоты для стора
```

### Ожидаемый ответ

```
# Протокол встречи: Запуск мобильного приложения v2.0

## Метаданные

- Дата: 14.10.2025
- Время: 11:00-12:00
- Место: Zoom
- Участники: Анна Смирнова (PM), Дмитрий Ковалёв (backend), Ольга Лебедева (дизайн), Игорь Петров (QA)

## Обсуждение

### Дата релиза

Изначально рассматривалась дата релиза 10.11. Игорь Петров возразил: на регрессионное тестирование не хватает 3 дней.

По итогу Анна Смирнова зафиксировала дату 12.11 как окончательную.

### Пуш-уведомления

Дмитрий Ковалёв дорабатывает API пуш-уведомлений. Пуш-уведомления согласованы как часть релиза v2.0.

### Онбординг

Ольга Лебедева готовит новые макеты онбординга.

### Аналитика

Обсуждался переход на Amplitude вместо Firebase. Анна Смирнова выступает за Amplitude, Дмитрий Ковалёв против: миграция событий займёт около 2 недель. Решение не принято.

### Платёжный SDK

Вендор обещал выпустить обновление платёжного SDK к 01.11. При задержке оплата в v2.0 останется на старой версии SDK.

### Материалы для стора

Требуется обновить release notes для стора. Необходимо уточнить у Олега из маркетинга вопрос о скриншотах для стора.

## Решения

1. Перенести релиз мобильного приложения v2.0 на 12.11.2025.
2. Включить пуш-уведомления в релиз v2.0.

## Задачи

| Задача | Ответственный | Срок |
| --- | --- | --- |
| Завершить разработку API пуш-уведомлений | Дмитрий Ковалёв | 24.10.2025 |
| Подготовить план регрессионного тестирования | Игорь Петров | 31.10.2025 |
| Показать новые макеты онбординга | Ольга Лебедева | не указан |
| Обновить release notes для стора | не указан | не указан |
| Уточнить у Олега из маркетинга вопрос о скриншотах для стора | не указан | не указан |

## Риски и открытые вопросы

- В заметках два срока релиза: «10.11» и «12.11»; принят более поздний и явный — 12.11.2025.
- Срок задачи «Показать новые макеты онбординга» указан размыто: «на следующей неделе».
- Не назначен ответственный: обновить release notes для стора.
- Не назначен ответственный: уточнить у Олега из маркетинга вопрос о скриншотах для стора.
- Не принято решение по системе аналитики: Amplitude или Firebase.
- Обновление платёжного SDK зависит от вендора (обещано к 01.11); при задержке оплата в v2.0 останется на старом SDK.
```

Этот же протокол, сконвертированный в Word: [examples/protocol_example.docx](examples/protocol_example.docx).

Что демонстрирует пример:

- противоречие в сроке релиза: выбран поздний и явный вариант («окончательно»), сомнение вынесено в риски;
- размытый срок «на следующей неделе»: в таблице `не указан`, исходная формулировка в рисках;
- задачи без ответственного («надо бы кому-то», «спросить у Олега»): `не указан` плюс пункт в рисках;
- Олег упомянут, но не присутствовал, поэтому в участники не добавлен;
- год в датах взят из даты встречи (14.10.2025), дата по дню недели не вычислялась;
- нерешённый вопрос (аналитика) не попал в решения и вынесен в риски.
